# Tempest 2000 SFX samples (Jaguar, 1994)

28 sound effects extracted from the `mwenge/tempest2k` source-code recreation
(github.com/mwenge/tempest2k, src/sounds/samples/ + src/images_sounds.s comment
table). Raw **signed 8-bit PCM, mono** (confirmed via the "zero" sample = all
0x00 and waveform endpoints settling near 0 -- NOT unsigned/128-biased).

Files are named by their original sample-table index (01-30, skipping 04/05
which the shipped Jaguar ROM excludes -- "Player Death"/"Player Death 2" show
Start=$00000000 in the table, i.e. not embedded in this build). manifest.json
carries name/priority/period/rate_hz/loop info per file, in file order.

## Pitch calibration

The Jaguar's tracker-style "period" field converts to a raw Hz value via the
Amiga Paula NTSC clock (`raw_rate_hz = 3579545 / period`) -- same convention
as our MOD player's period table. This raw formula was *initially* validated
against sample `06`'s own embedded metadata (it's an un-stripped Amiga 8SVX
file with a real `samplesPerSec=8363` field, matching `3579545/428=8363.4`
almost exactly) -- but that validation turned out to be **misleading**: file
`06` is a leftover, unconverted ORIGINAL Amiga export (complete with
`8SVX`/`VHDR`/`NAME`/`ANNO`/`BODY` IFF chunks we had to strip), so its
embedded rate describes what it was authored at on an Amiga, not how the
Jaguar's own (closed-source, unavailable) DSP driver actually plays these
samples back. The two pipelines don't share a clock.

**Empirically calibrated correction: `rate_hz = raw_rate_hz * 2.75`.**
Found by ear (real hardware playback of a 2x/2.5x/2.7x/2.75x/3x/4x A/B sweep
against the raw-formula rate, which sounded "way too slow" -- confirmed
2.75x was correct). `manifest.json` keeps both `rate_hz_raw` (the raw
Amiga-period-formula value, kept for provenance/audit) and `rate_hz` (the
actual calibrated value baked into `src/audio/sfx_data.h/.cpp`'s `TABLE`
and used at playback). If more samples get added later, apply the same
2.75x correction to their raw formula value -- do not re-derive from
sample 06's header again.

**EXCEPTION -- `SFX_SPIKE` ("Tink For Spike", file `14`) is NOT given the
2.75x.** It stays at its raw Jaguar period value (`3579545/254 = 14092.7`
Hz; `rate_hz == rate_hz_raw` in the manifest). The 2.75x is correct for
the lower-pitched samples but over-shifts this high-frequency tink so that
~64% of its energy lands at ~18.9 kHz, above the 3DS speaker's ceiling --
i.e. inaudible. The Jaguar also never plays the table period: `decspike`
overrides it with `(length & 0x1FF) + 524` and ramps the pitch up as the
spike is shot down. Full write-up (why + how + tuning knob):
`docs/validation/spike-sfx-ramp-2026-09-19.md`. Do not re-apply 2.75x to
this entry.

## Loudness calibration

Per-sound `gain` in the baked `TABLE` is target-RMS loudness normalization:
`gain = round(35.0 / sample_rms, 2)` clamped to `[0.5, 2.5]`, computed on the
extracted signed-8-bit payload. Three voice samples (22/23/24 -> GROOVY/YES/
SUPERZAP) additionally went through a one-off local-RMS AGC + soft-limit +
peak-normalize mastering pass (repo commit `683d14a` -- SUPERZAP's spoken
phrase was RMS 2-11 behind a RMS-44 transient and uniform gain couldn't lift
it); their bank BYTES and rebaked gains are frozen verbatim. The bank is
(re)generated by `tools/gen_sfx_bank.py`, which regenerates every raw entry
from these assets (asserting bit-identity against the shipped bank), carries
the three mastered voice entries forward frozen, and applies the gain law
above to anything newly added. Never hand-edit `src/audio/sfx_data.{h,cpp}`.

## Format used in-game

Native **8-bit signed PCM** on both platforms (3DS: `NDSP_FORMAT_MONO_PCM8`
directly, no upconversion; desktop: wrapped in an in-memory 8-bit *unsigned*
WAV, re-biased +128, for `SDL_mixer`'s loader). An earlier pass upconverted
to 16-bit while ruling out format as a variable during an unrelated crash
investigation (the actual bug was a stale-build/missing-`-MMD` Makefile
issue, not audio format) -- reverted once that was confirmed, since native
8-bit is simpler and uses half the memory.

## Event mapping vs. the real Jaguar game

Where feasible, trigger mappings were checked against the actual Jaguar
`yak.s` source (a leaked commercial disassembly-with-comments; used here only
to extract small factual data points -- which numeric sound ID a routine
selects and why -- not reproduced). Confirmed corrections from this pass:

- **Powerup pickup -> "Warp"** (not "Get Power Up"): the routine that awards
  a powerup is annotated "we're going to do a power-up" immediately before
  selecting the Warp sound.
- **Powerup capsule spawn -> "Powered Up Shot"** (not "Pulse For Pulsar"):
  the routine that fires the traveling powerup object is annotated as
  drawing/sounding "a Power Up shot."
- **Level-transition powerup pickup ("yea yea yea")**: not a static chord.
  The real routine retriggers one "yes"-family sample repeatedly with a
  continuously RISING pitch during the climb-out (a pitch register starts
  around a mid-range value and steps up a small fixed amount on every
  repeat, alternating between two near-identical "yes" variants -- which is
  why it reads as "the same yes, sped up each time" rather than a chord).
  Our port uses a single sample (`SfxId::YES`, user's choice) retriggered 5
  times with increasing pitch to match that ramp, rather than the original's
  two alternating variants.

Other mapped events (fire, explosion, spike, zapper, multiplier fanfare,
death, reflect, warp-between-levels) are close semantic matches by sample
name, not yet cross-checked against specific `yak.s` routines.

Used (not the earlier the reference build PCM-sample-per-.dat scheme, which was replaced by
chiptune-only audio in the shipped PC-port binary -- no original SFX data
survives). Tempest 2000 is the closest same-genre, well-documented source.
Tempest-2000-1994-(c)-Atari/Interplay; used here as reference SFX for a
non-commercial fan port, same spirit as the shipped MOD chiptune already in
the game.
